# Модуль «Ближайшие матчи» (backend)

Закрывает три места интерфейса: виджет на главной, раздел «Ближайшие матчи» из бокового меню и страницу «Смотреть все» со всеми матчами игрового дня.

## Эндпоинты

```
GET /api/v1/matches/upcoming?limit=4
GET /api/v1/matches/matchday?date=2026-09-19
```

`upcoming` обслуживает и виджет, и раздел меню — разница только в `limit`, поэтому эндпоинт один. Отдаёт матчи ближайших дней, где хотя бы одна команда входит в топ своей лиги по угловому индексу. Порядок хронологический: блок называется «Ближайшие», индекс здесь фильтр, а не сортировка.

`matchday` отдаёт все матчи топ-5 лиг за игровой день, без отбора по индексу, но со значениями индекса в карточках. Если в запрошенный день матчей нет — пауза на сборные, понедельник, — возвращается ближайший игровой день, а `isRequestedDate` становится `false`. Интерфейсу нужно это показать, иначе пользователь решит, что видит сегодняшние матчи.

## Состав

| Файл | Назначение |
|---|---|
| `matches.controller.ts` | Два эндпоинта, валидация параметров |
| `matches.service.ts` | Выборка, отбор, кэш, сборка ответа |
| `selection.util.ts` | Правило отбора по индексу и выбор игрового дня — чистые функции |
| `time.util.ts` | Пояса: время источника → UTC, границы суток по поясу сервиса |
| `fixtures.parser.ts` | Разбор `fixtures.csv` |
| `fixtures-ingest.service.ts` | Загрузка расписания в базу, идемпотентный upsert |
| `fixtures-ingest.processor.ts` | Фоновая задача BullMQ |
| `matches.config.ts` | Все продуктовые константы |
| `../../prisma/schema.matches.prisma` | Полная Prisma-схема: `League`, `Team`, `TeamAlias`, `Fixture`, `CornerIndexSnapshot` |

Продуктовая логика вынесена в `selection.util.ts` и `time.util.ts` намеренно: это единственное место, где живёт правило «какие матчи считать интересными», и оно покрывается тестами без базы, Redis и Nest.

## Конфигурация

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MATCHES_LEAGUES` | `E0,SP1,I1,D1,F1` | Лиги сервиса |
| `MATCHES_TOP_TEAMS_PER_LEAGUE` | `6` | Сколько команд лиги считается «высоким индексом» |
| `MATCHES_WIDGET_LIMIT` | `4` | Карточек в виджете главной |
| `MATCHES_UPCOMING_WINDOW_DAYS` | `10` | Насколько вперёд ищем ближайшие матчи |
| `MATCHES_MATCHDAY_LOOKAHEAD_DAYS` | `14` | Насколько вперёд ищем непустой игровой день |
| `MATCHES_SERVICE_TZ` | `Europe/Moscow` | Пояс, в котором определяется игровой день |
| `MATCHES_SOURCE_TZ` | `Europe/London` | Пояс, в котором источник указывает время начала |
| `MATCHES_FIXTURES_URL` | `https://www.football-data.co.uk/fixtures.csv` | Файл расписания |
| `MATCHES_INGEST_CRON` | `17 * * * *` | Как часто обновляем расписание |
| `MATCHES_CACHE_TTL` | `120` | TTL кэша ответов, секунды |

Размер топа вынесен в конфигурацию не для красоты: это продуктовый параметр, и аналитики должны двигать его без релиза.

## Подключение

1. Задать `DATABASE_URL` и создать миграцию:

	```powershell
	$env:DATABASE_URL = "postgresql://matchlab:matchlab@localhost:5432/matchlab"
	npx prisma migrate dev --schema .\prisma\schema.matches.prisma --name matches-relations
	npx prisma generate --schema .\prisma\schema.matches.prisma
	```

2. Заполнить `League` кодами `E0`, `SP1`, `I1`, `D1`, `F1`, затем `Team` и `TeamAlias`. Без алиаса матч с неопознанной командой не попадёт в базу.
3. Добавить `MatchesModule` в `AppModule`.
4. После пересчёта углового индекса вызывать `MatchesService.invalidateCache()`, иначе подборка будет отставать на время TTL.

Связи `Fixture` и `CornerIndexSnapshot` с командой используют составной внешний ключ
`(leagueCode, teamId)`. Поэтому база не позволит случайно привязать команду другой лиги.

## Что стоит знать до интеграции

**Расписание и статистика — разные файлы источника.** Сезонные файлы `E0.csv` и подобные содержат только сыгранные матчи, будущих в них нет. Календарь лежит отдельно, в `fixtures.csv`, и покрывает примерно неделю вперёд. Отсюда `MATCHES_UPCOMING_WINDOW_DAYS = 10`: ставить больше бессмысленно, источник дальше не заглядывает.

**Время начала в источнике лондонское, не UTC.** Прямого подтверждения этому в документации источника я не нашёл — вывод сделан по составу файла (британский сайт, британские дивизионы, времена вида 15:00 и 19:45, характерные для английского календаря). Проверить стоит на первом же реальном туре: если матчи поедут на час, дело в `MATCHES_SOURCE_TZ`.

**Граница суток.** Матч в 22:00 по Лондону — это уже следующий день по Москве, и на странице игрового дня он окажется завтра. Так и задумано: пользователь видит свой календарь, а не британский. Тест на этот случай есть.

**Загрузка идемпотентна.** Файл расписания перезаписывается источником целиком, поэтому ключ идемпотентности собирается из источника, лиги, даты и названий команд. Повторная загрузка обновляет время начала, но не трогает статус и счёт: их ведёт другой процесс, и затирать результат сыгранного матча перезалитым расписанием нельзя.
